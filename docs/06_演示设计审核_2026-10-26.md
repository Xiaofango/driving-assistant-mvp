# DA MVP 演示设计审核

审核时间：2026-10-26 22:43（北京时间）。范围：当前单页 CARLA 演示、DA 逻辑与网关、14 项测试、5 份整理后的业务文档、8 页可编辑演示稿。原始上游资料只用于核对范围，不将路线图当作已实现功能。

后续界面调整：页面首页现只突出“设置仿真跟车距离”和“查询仿真驾驶状态”；路径请求、模拟告警、安全拒止已折叠并明确标注。下文有关旧版界面措辞的发现保留为审核记录；车辆卡住、轨迹未验证、状态新鲜度和 PPT 更新等问题仍待解决。

交互补强：服务现依据用户原话、CARLA 快照和网关回执生成差异化回复，并在交互记录中展示判断理由、依据和设置/路线记录变化。支持明确跟车等级、自然说法、ETA 查询和无实时路况时的拒绝推断；自动测试增至 20 项。该能力仍由受限规则实现，未接入开放式语言模型。

## 结论

当前版本适合有人值守的内部概念演示：真实 CARLA 画面、实时车速、文本指令、仿真参数设置和安全拒止已经连成一页。**还不适合不重置、连续讲解的正式演示**。审核时车辆在地图边缘撞到树旁环境后长时间不动，页面却仍显示自动驾驶 `ACTIVE`；路线比较也变成 0.2 分钟对 0.2 分钟。演示稿仍描述旧版命令行和内存仿真，无法准确介绍当前成果。

下文的优先级按现场演示风险排序。P0 表示会直接破坏核心演示，P1 表示会误导观众或使安全/成功语义失真，P2 表示稳定性与可维护性问题。

## 已验证的部分

- 本机 CARLA 0.9.16 在低画质下运行；前视、车外视角均可返回有效 JPEG，浏览器同时显示画面与交互区。
- 在先前实测中，车速会随仿真运动变化；“跟车距离调远一点”调用 Traffic Manager 设置，等级从 2/5 米变为 3/7 米；“换一条更快的路”调用 `set_path` 并改变页面中的路线 ID。
- 注入紧急接管告警后，DA 不向跟车/路线网关发写调用。桌面 1600×900、1366×768 和移动宽度无横向溢出。
- `python -m unittest discover -s tests -q` 当前 14 项通过。测试使用内存网关或 CARLA 测试替身，**不**证明 CARLA 运行路径一直可用。

## 问题与证据

### P0 · 车辆可能卡住，画面仍显示 ACTIVE

只读运行检查时，演示车辆 30 秒内位置始终约为 `(-117.3, 52.7)`、车速 0 km/h，控制量持续 `throttle=0.85`、`brake=0`，交通灯为绿灯。前视画面显示车辆贴近树和步行区域；没有近距离其他车辆。页面仍显示 TM 自动驾驶 `ACTIVE`。这与等红灯不同，更像仿真车碰到地图物体后无法脱困。见 [现场画面](../.build/audit-stuck.jpg) 与 [单页状态](../.build/audit-current.png)。

生成点、绕行点和终点目前按三维直线距离从出生点列表挑选，随后直接交给 Traffic Manager，没有连续道路拓扑、可行驶车道、转向约束或到达监测：[carla_gateway.py](../da_mvp/carla_gateway.py) 第 70–104 行。这个选择方法无法保证路线能顺利跑完。

**建议先修：**预先选定一条实测可行的道路环线，用 CARLA waypoint 路网构造途经点；接入碰撞或卡住检测（例如持续 8–10 秒速度接近 0 且不是红灯/主动停车），自动提示操作员重置或重新生成车辆。页面把“自动驾驶已启用”与“车辆正在移动/卡住”分开展示。

### P1 · “更快路线”缺少真实道路验证，且会失去可演示性

审核时 `/api/state` 返回原始路线和备选路线均为 **0.2 分钟**，所以场景卡片没有可展示的节省值。ETA 使用当前位置到途经点/终点的欧氏直线距离除以固定 500 米/分钟，并保留一位小数；未计算道路长度、转弯、红灯或拥堵：[carla_gateway.py](../da_mvp/carla_gateway.py) 第 172–195 行。路线提交的成功条件是 `tm.set_path` 没有抛异常，`current_route_id` 随即本地改为 `route_b`；代码没有确认车辆实际转向、走到目标路线或到达目的地：同文件第 215–229 行。

“更快”只相对于这套几何估算成立，不能被讲成 CARLA 证实了更短行驶时间。即使文案已有“几何估计”，卡片的“动态路线切换”和“当前正在使用”仍可能被理解为实际行驶路径已验证。

**建议：**把路线改为固定、路网可行的 A/B 方案，显示道路里程和“演示估计”；记录车辆沿路径的 waypoint 进度。仅在至少一个候选 ETA 明显更低时启用场景卡片，否则显示“当前无可比较路线”。若需要讲真实节时，接导航引擎或对两条路线多轮仿真测时。

### P1 · 状态新鲜度检查对 CARLA 模式基本无效

文档写着“写操作前快照不超过 5 秒”，测试也覆盖了一个人工调旧时间戳的内存状态：[02_接口与安全.md](02_接口与安全.md)、[test_da_mvp.py](../tests/test_da_mvp.py) 第 56–61 行。但 CARLA `snapshot()` 每次读取时把 `timestamp` 设为当前系统时间，而非 CARLA 世界 tick 或传感器数据采集时间：[carla_gateway.py](../da_mvp/carla_gateway.py) 第 178–195 行。摄像头的 `camera_available` 仅检查曾经收到过帧；若回调停止，旧 JPEG 仍可一直作为“实时画面”返回。同文件第 135–150 行。

**建议：**分别保存 CARLA 世界快照、车速读数和摄像头帧的实际采集时间；超过阈值时显示“画面/状态延迟”，禁止依赖过期状态的写操作。测试中模拟传感器停止和 CARLA 断连。

### P1 · 接管告警与 NOA 名称容易造成能力误读

页面的接管告警来自操作台 `/api/event` 手动注入；没有真实 ADAS/DMS 事件源：[web_demo.py](../da_mvp/web_demo.py) 第 116–119 行。页面左下只写 `ADAS EVENT` 和“紧急接管告警”，需要更醒目的“模拟注入”字样。告警仅影响 DA 的回复与写操作，仿真车不会因这个事件自动接管或停车。

“关闭 NOA 测试拒止”实际调用的是 CARLA Traffic Manager 的 `set_autopilot(False)`，并向仿真车施加一次制动：[carla_gateway.py](../da_mvp/carla_gateway.py) 第 243–255 行。这是演示操作台控制，不是量产车 NOA。**建议：**按钮改为“关闭仿真自动驾驶”，告警改为“注入模拟接管告警”，并在画面状态中明确“仿真 TM / 人工事件”。

### P1 · PPT 与新版演示脱节

[DA_MVP_方案与演示.pptx](../slides/DA_MVP_方案与演示.pptx) 共 8 页，可正常渲染，版式没有明显裁切。但第 1 页仍叫“离线演示”，第 3 页称“当前仓库仅实现 DA 与内存仿真网关”，第 5/7 页用 18→15 分钟的静态案例并让观众运行 `python -m da_mvp.demo`，第 8 页交付清单仍仅写内存仿真。这与已安装、已运行的 CARLA 单页演示不一致。[03_实施与验收.md](03_实施与验收.md) 也沿用旧命令行演示脚本。现场若先讲 PPT 再打开网页，观众会听到两套不同的完成状态。

**建议：**演示稿改为“离线逻辑 + CARLA 实时仿真”双层成果；放入当前单页真实截图；第 5/7 页使用不依赖固定分钟数的场景脚本，注明 ETA 来源和人工告警；第 8 页列出 CARLA 接入与尚未接入 PC/MQTT/真实 ADAS 的边界。同步改写 [03_实施与验收.md](03_实施与验收.md)。

### P2 · 页面复位和故障处理不够稳

`DemoState.reset()` 先关闭旧网关，再创建新 CARLA 场景。如果重新生成车辆/摄像头失败，旧场景已经销毁、`state.gateway` 可能不可用：[web_demo.py](../da_mvp/web_demo.py) 第 27–33 行。HTTP 处理器只把 `ValueError` 转成结构化错误；CARLA 超时、场景生成失败等异常可能直接中断连接：同文件第 99–131 行。摄像头回调吞掉所有异常，操作员只能看到“等待画面”，无法判断原因：[carla_gateway.py](../da_mvp/carla_gateway.py) 第 135–146 行。

**建议：**复位前先验证新场景可用，失败时保持或可恢复旧场景；对 API 返回明确的失败 JSON；页面显示 CARLA 连接、传感器帧时间和错误原因；记录简短诊断日志。

### P2 · 交互范围比“机器人聊天”窄

当前是文本输入和少量关键词规则，没有 ASR/TTS、PC 会话接入或开放式对话：[intent.py](../da_mvp/intent.py) 第 12–28 行。例如“跟车距离设成四级”“换更快路线”不一定能完成，通常会走澄清。该保守规则保护写操作，但讲解时应称为“受限驾驶话术演示”，避免承诺自然语言覆盖率。后续若扩展语义解析，仍应让代码与网关负责权限、数值范围和执行确认。

### P2 · 自动化覆盖集中在替身网关

[test_web_demo.py](../tests/test_web_demo.py) 的 `CarlaGateway` 是继承内存网关的测试替身，测试页面 API 传输和安全分支，不检查真实车辆移动、相机停帧、路径进度、碰撞、断连或重置失败。14 项通过与现场卡住并不矛盾。

**建议：**增加一个可手动或在专用机器上运行的 CARLA 端到端验收脚本：启动后等待连续不同帧、车速曾大于阈值、路径切换后的 waypoint 进度、异常时结构化报错；将运行数据保存在验收记录中。

## 修复顺序

1. **先保证车辆能持续跑：**固定可行道路路线、卡住检测、可靠重置。这个问题影响“实时车辆运行”的核心观感。
2. **再让数值和标签准确：**道路路线可比较；将提交请求、实际执行与到达结果分开；为人工事件和 TM 控制加显式标签。
3. **然后更新材料：**PPT 第 1、3、5、7、8 页和实施验收文档统一到当前 CARLA 版本。
4. **最后补故障演示与验收：**状态采集时间、相机停帧、断连、复位失败的清晰反馈与 CARLA 端到端脚本。

## 审核方法与边界

- 使用 graphify 的 Python AST 提取器检查代码结构：117 个节点、213 条已提取关系；结论仍由逐文件检查和运行观测确认。
- 只读采样了运行中的 `/api/state` 与 `/api/frame`；10 次摄像头读取均得到不同帧，状态请求中位数约 4 ms，图片请求中位数约 19 ms。不同帧可能来自场景中的其他物体，不能据此证明自车在移动。
- 通过 CARLA 客户端连续 30 秒读取自车位置、速度、控制量和交通灯，确认卡住现象。没有对用户当前仿真状态执行重置或路线更改。
- 演示稿用本机 PowerPoint 导出 8 页 PNG 并检查关键页；14 项自动测试重新运行，全部通过。
- 计划用 TypeSafe Jev 对三处用户可见标签做辅助语义判断，实际调用返回 HTTP 451，**没有得到模型判断**；本报告所有结论均以代码、页面和 CARLA 观测为依据。请求、失败记录保存在 `../.build/audit_typesafe_request.json` 与 `../.build/audit_typesafe_run_20261026/`。
